# Collaborative Todo List

Это приложение для совместного управления списком задач в режиме реального времени, разработанное в рамках тестового задания.

## Технологический стек
- **Backend:** NestJS, Prisma, PostgreSQL
- **Frontend:** Next.js (App Router), TailwindCSS, Zustand, Framer Motion
- **Коммуникация:** HTTP (REST API) и WebSocket (Socket.IO)

## Инструкция по запуску

Проект полностью контейнеризован. Для запуска вам потребуется только Docker и Docker Compose.

### Переменные окружения (.env)
В проекте используются переменные окружения для настройки базы данных и секретных ключей. 
По умолчанию все необходимые переменные уже прописаны прямо в `docker-compose.yml`, поэтому вам **не нужно** вручную создавать `.env` файлы для запуска через Docker. Приложение запустится "из коробки".

Если вы захотите запустить проект локально без Docker (через `npm run start:dev`), вам потребуется создать файл `.env` в папке `backend` со следующим содержимым:
```env
DATABASE_URL="postgresql://postgres:postgres@localhost:5433/collaborative_todo?schema=public"
JWT_SECRET="super-secret-key-change-me-in-production"
JWT_EXPIRATION="24h"
PORT=3000
FRONTEND_URL="http://localhost:3001"
```

1. Убедитесь, что Docker запущен.
2. Откройте терминал в корневой директоре проекта и выполните команду:
   ```bash
   docker compose up --build -d
   ```
3. Дождитесь, пока контейнеры соберутся и запустятся. Приложение будет доступно по адресам:
   - **Frontend:** http://localhost:3001
   - **Backend API & WebSockets:** http://localhost:3000

*База данных будет автоматически инициализирована стартовыми данными (seed), поэтому в приложении уже будет создано два пользователя и один общий список.*

## Инструкция по тестированию совместной работы

Чтобы проверить функционал реального времени и обработку конфликтов, выполните следующие шаги:

1. Откройте **обычную вкладку** браузера и перейдите на [http://localhost:3001](http://localhost:3001).
2. Нажмите кнопку **"Войти как Alice (Admin)"**. Вы попадете в общий список задач.
3. Откройте **вкладку в режиме инкогнито** (или другой браузер) и перейдите на [http://localhost:3001](http://localhost:3001).
4. Нажмите кнопку **"Войти как Bob (Member)"**. Вы окажетесь в том же самом списке.

**Что нужно проверить:**
- **Синхронизация в реальном времени:** Добавьте задачу в одной вкладке — она мгновенно появится в другой.
- **Индикация присутствия (Presence):** Начните редактировать задачу от имени Alice (кликните по тексту задачи). Bob увидит пульсирующую точку рядом с задачей и специальный значок блокировки.
- **Drag & Drop:** Измените порядок задач, перетащив их за иконку слева — порядок моментально обновится у второго пользователя.
- **Офлайн-режим:** Отключите интернет (или остановите backend контейнер), добавьте/отметьте несколько задач. Они сохранятся локально в очереди. Как только соединение восстановится, изменения будут отправлены на сервер.
- **Права доступа:** Зайдите за Bob (Member) и попробуйте удалить задачу, созданную Alice. Сервер запретит это действие. Удалять чужие задачи может только Admin (Alice). Также попробуйте удалить завершенную (зачеркнутую) задачу — это можно сделать только с подтверждением (форсированно) из-под админа.

## Архитектурные решения и обработка конфликтов

- **Конкурентное редактирование (Optimistic Locking):** У каждой задачи есть поле `version`. При редактировании фронтенд отправляет серверу текущую известную версию задачи. Если версия в БД уже больше (кто-то другой успел сохранить изменения), бэкенд возвращает `ConflictException`, а фронтенд откатывает изменения до актуальной серверной версии. Это реализует стратегию *Last-write-wins (со строгим контролем)* и защищает от случайной затирки данных.
- **Синхронный Drag & Drop (Fractional Indexing):** Для сортировки задач используется алгоритм дробных индексов (как в Jira или Figma). При перемещении задачи ей присваивается строковый `position`, лексикографически находящийся строго между соседними элементами. Это позволяет менять порядок без необходимости пересчитывать позиции всех остальных элементов в БД, что полностью исключает конфликты порядка при одновременном Drag & Drop.
- **Удаление во время редактирования (Soft Deletes):** Задачи не удаляются физически, а помечаются как удаленные (`deletedAt`). Это гарантирует, что если кто-то пытается сохранить отредактированную задачу, которая была только что удалена другим пользователем, сервер корректно обработает эту ситуацию (вернет ошибку) и клиентское приложение не упадет из-за нарушения ссылочной целостности.

## Что не было реализовано (и как это можно сделать)

В рамках ограничения по времени приоритет был отдан сложным распределенным сценариям, UX и обработке конфликтов. Некоторые базовые фичи были опущены:

- **Полноценная регистрация и отправка email-инвайтов:**
  *Как бы реализовал:* Подключил бы Nodemailer (или сервис типа Resend) на бэкенде. При отправке инвайта создавался бы токен (уже частично реализовано в `lists.service.ts`), генерировалась ссылка и отправлялась на почту. По клику на ссылку пользователь попадал бы на страницу ввода пароля для регистрации/привязки аккаунта к списку.
- **Уведомления (Notifications):**
  *Как бы реализовал:* Добавил бы отдельную сущность `Notification` в БД. При критичных событиях (вас пригласили, важную задачу удалили) создавалась бы запись. В WebSockets можно добавить событие `notification:new`, чтобы в реальном времени показывать toast-уведомления (через библиотеку `react-hot-toast`).
- **Сложное слияние (Merge) при конфликтах редактирования:**
  *Как бы реализовал:* Сейчас при конфликте версий сервер просто отклоняет изменение. Можно доработать UI: при получении 409 Conflict показывать модальное окно с выбором "Оставить вашу версию" / "Принять версию с сервера" / "Объединить", отправляя на сервер итоговый результат с ключом `force=true`.
